# Tokens

<Lede>
  A token is a named value - a hex code, a number of pixels, a font weight. We store the values
  once, give them paths, and reference the paths everywhere else.
</Lede>

<ArticleMeta />

## Tokens are values

Most styling decisions are values: a colour, a length, a font size. The question is where the
values live. If they live inline at the call site (`<div style={{ color: '#1C1917' }} />`), every
consumer holds its own copy, and changing the colour means hunting through the codebase. If they
live in a flat object (`palette.ink`), there is one copy but no structure - no way to model the
difference between _the colour ink_ and _the foreground of a button_.

Motif organises tokens as a tree. Scales at the top (`colors`, `space`, `radii`), nested as deeply
as the design needs underneath.

<CodeBlock lang="ts" code={`const tokens = {
  colors: {
    ink: '#1C1917',
    paper: '#FBF7F2',
    blue: { 500: '#2563EB', 600: '#1D4ED8' },
  },
  space: { 1: 4, 2: 8, 4: 16 },
  radii: { sm: 4, md: 8, lg: 12 },
};`} />

Every leaf has a path: `colors.ink`, `colors.blue.500`, `space.4`. That path is how the rest of the
library refers to the value.

## Two layers, one tree

The values themselves are only half the story. A design system also has to say _what a value is
for_. The colour `#1C1917` is the colour ink. But the foreground of a button is also the colour
ink - except in dark mode, when it's the colour paper.

So tokens come in two kinds. They live in the same tree.

**Primitives** are the palette. Literal hex codes, literal pixel counts. They don't change with the
theme.

<CodeBlock lang="ts" code={`colors: {
  ink:   '#1C1917',
  paper: '#FBF7F2',
  blue:  { 500: '#2563EB', 600: '#1D4ED8' },
},`} />

**Semantics** name an intent. They reference primitives by path, prefixed with `$`.

<CodeBlock lang="ts" code={`colors: {
  text:    { default: '$colors.ink',   inverse: '$colors.paper' },
  surface: { base:    '$colors.paper', inverse: '$colors.ink'   },
  action:  { primary: { bg: '$colors.blue.600', fg: '$colors.paper' } },
},`} />

When the theme switches, only the semantic layer rebinds. The primitives stay put. A button still
asks for `$colors.action.primary.bg`, and that path resolves to a different blue.

## References walk the tree

A `$`-prefixed string is a reference, not a value. The resolver walks the dotted path against the
active theme:

<CodeBlock lang="ts" code={`'$colors.blue.500'; // → '#2563EB'
'$colors.action.primary.bg'; // → '$colors.blue.600' → '#1D4ED8'`} />

If a reference points at another reference, the resolver keeps walking until it hits a literal.
That is how a semantic name can sit one indirection above the palette without the consumer code
knowing or caring.

## Fallback chains and component tokens

A reference can name alternatives with `??`. The resolver takes the first one the theme defines,
and a last alternative that is not a reference is a literal default:

<CodeBlock lang="ts" code={`'$components.button.primary.bg ?? $colors.action.primary.bg';
'$components.card.borderRadius ?? $radii.lg ?? 12px';`} />

On web a chain becomes nested CSS fallbacks,
`var(--components-button-primary-bg, var(--colors-action-primary-bg))`, so it costs nothing at
runtime. On native the resolver walks the alternatives in order.

The kit's recipes use this to read a third layer, `components`, before the semantic one. A theme
that defines nothing there gets the kit's usual look. A theme that wants a different button
without forking the kit sets the paths it cares about:

<CodeBlock lang="ts" code={`import { createTheme } from 'usemotif';
import { lightTheme } from '@usemotif/tokens';

export const brand = createTheme({
  ...lightTheme,
  name: 'brand',
  tokens: {
    ...lightTheme.tokens,
    components: {
      button: { primary: { bg: '$colors.green.600' }, borderRadius: '$radii.full' },
      card: { borderRadius: '$radii.sm' },
    },
  },
});`} />

The paths are `<recipe>.<variant value>.<prop>` for a variant and `<recipe>.<prop>` for the base:
`button.danger.color`, `input.invalid.borderColor`, `card.interactive.hover.borderColor`. Every
colour and radius the recipes set has one. A component token holds a reference or a CSS string;
a bare number is emitted without a unit.

## Font sizes follow the reader

A number in `fontSizes` is authored in px and emitted on web in `rem`, so `md: 16` becomes
`--fontSizes-md: 1rem` and a reader who raises the browser's text size gets larger text. On
React Native, `Text` and `Input` already follow Dynamic Type on iOS and the font scale on Android.

A layout that can't take unlimited growth sets a cap:

<CodeBlock lang="ts" code={`createTheme({
  name: 'light',
  tokens: { ...lightTheme.tokens, fontScale: { max: 1.5 } },
});
// web:    --fontSizes-md: min(1rem, 24px)
// native: <Text maxFontSizeMultiplier={1.5}>, unless the prop is set`} />

The default themes set no cap. `rem` is relative to the root element, so an app that changes the
`html` font size, such as the `62.5%` trick, scales its font-size tokens with it.

## `createTheme` types the tree

A theme is a name plus a token tree:

<CodeBlock lang="ts" code={`interface Theme {
  readonly name: string;
  readonly tokens: TokenMap;
}`} />

`createTheme` is a thin factory. It does not transform the input - it preserves the literal
token shape, which is what makes the paths derivable. `$`-references autocomplete against this
theme once you declare it; see [Token autocomplete](/guides/token-autocomplete) for the one-time
setup.

<CodeBlock lang="ts" code={`import { createTheme } from 'usemotif';

export const lightTheme = createTheme({
  name: 'light',
  tokens: {
    colors: {
      ink: '#1C1917',
      paper: '#FBF7F2',
      text: { default: '$colors.ink', inverse: '$colors.paper' },
      surface: { base: '$colors.paper', inverse: '$colors.ink' },
    },
    space: { 1: 4, 2: 8, 4: 16 },
    radii: { sm: 4, md: 8, lg: 12 },
  },
});`} />

The returned object is exactly the input. The work happens at the type level:
`lightTheme.tokens.colors.text.default` is statically known, and `<Box bg="$colors.surface.base" />`
is checked against the theme's actual shape.

## One tree, two renderers

Tokens are the canvas every renderer paints on. On web, motif emits each leaf as a CSS custom
property - `$colors.surface.base` becomes `var(--colors-surface-base)` - and switches values by
setting `data-theme` on `<html>`. On native, the same tree lives in memory; the runtime resolver
reads from it directly.

The two renderers never see each other's output. They both see the same tokens.
