# Compiler

<Lede>
  The compiler reads your source, finds the style props it can resolve at build time, and emits
  CSS rules into the build output. Everything it cannot resolve falls through to the runtime -
  same component, same prop, slower path. The compiler is an optimisation, not a contract.
</Lede>

<ArticleMeta />

## The runtime path always works

The first thing to know about motif's compiler is that you do not need it. A motif app with no
bundler plugin renders correctly. Every style prop, every variant, every responsive object
resolves at render time through the runtime resolver, and the resulting class names land on
the page.

The compiler does the same work earlier. When a build plugin is wired in, the compiler reads
your source, evaluates the style bags it can prove are static, and emits the resulting CSS
rules into the build output. The runtime then notices those rules are already on the page and
skips the emission.

Two paths; the same output. The compiler trades build time for render time.

## What it extracts

The compiler is conservative. It only resolves a style bag statically when it can prove the
bag has no runtime dependencies - every value is a literal, a `$`-reference to a known token,
or a responsive object whose keys are all known breakpoints.

That covers the majority of real code:

- Every `base` block inside a `styled()` call.
- Every variant value inside `styled().variants`.
- Style props passed inline with literal or token values.

It does not cover:

- A style bag built from a function call (`bg: getColor(name)`).
- A value held in a prop the call site passes in (`<Box p={padding} />`).
- A spread from a variable defined in a different module (`<Box {...overrides} />`).

For those, the runtime resolver does the work. The compiler bails on the bag, leaves the prop
intact, and the rendered component still produces the correct CSS - just at render time
instead of build time.

## What gets emitted

For the bags the compiler can extract, the output depends on the build target.

**On web**, the compiler emits:

- One CSS rule per unique style bag, hashed into a class name.
- Media-query wrappers for responsive slots.
- `:hover` / `:focus` / `:active` / `:disabled` rules for the pseudo-state namespaces.
- `::before` / `::after` rules for literal `_before` / `_after` bags, with the same default
  `content` the runtime gives them, so an element using them can still become a plain tag.
- A `<style>` block injected into the bundle entry, plus a hashed-class map the runtime reads
  to know which classes already exist.

**On native**, the compiler emits:

- A static style-object literal per unique bag.
- A const lookup that the runtime resolver uses instead of evaluating the bag at render.

Both targets share the safety analysis. Either path produces the same component, the same
class name set on web, and the same React Native style object on native.

## Safety analysis

Before extracting, the compiler runs an analysis pass over every `<Box>` and every `styled()`
call site. It classifies each JSX attribute as one of:

- **Static.** A literal or a known token reference. Extractable.
- **Dynamic.** A spread, a function call, a variable lookup whose value depends on render
  state. Not extractable; leave alone.
- **Mixed.** Some attributes are static, some are dynamic. The compiler extracts the static
  ones into a class and leaves the rest as runtime props.

The mixed case is the common one. A `<Box p="$space.4" bg={color} />` can ship the `p` as a
class and the `bg` as a runtime prop. The runtime resolver sees the class is already attached
and only emits CSS for `bg`.

This is what makes the compiler progressive: a single component can have part of its styling
inlined at build time and part resolved at render time. The split is invisible at the call
site.

## Plugins for every bundler

The same compiler core ships behind a thin adapter for every major bundler.

- `@usemotif/compiler-babel` - the core Babel plugin. Use directly in a Babel-driven build.
- `@usemotif/compiler-web` - universal web-bundler plugin (`unplugin`, Babel-based under the hood). Vite, Next.js, webpack, Rollup, Rspack, esbuild, Farm.
- `@usemotif/compiler-metro` - Metro transformer. React Native bare and Expo.

Each adapter wraps the compiler-core analysis in the host's transform API. The configuration
surface is small - typically a single options object naming the sources to scan (`usemotif`,
`@usemotif/react`, `@usemotif/react-native`, plus any local re-exports).

[Bundlers](/bundlers/vite) covers the per-bundler installation. The
[compiler-core reference](/reference/compiler-core) covers the public API for plugin authors.

## Debugging extraction

When a style bag does not get extracted, the source of truth is the compiler's output. Every
plugin supports a `verbose` option that logs each bag's classification.

<CodeBlock lang="ts" code={`// vite.config.ts
motif.vite({ verbose: true })`} />

The log entry tells you whether the bag was static, dynamic, or mixed, and what flagged it as
dynamic if it failed. The most common cause is a value imported from a different file that the
analyser cannot follow - the cure is to inline the value or to re-export it through the
package's main entry.

You do not need to debug the compiler to ship a working app. Every bag falls through to the
runtime path. Debug when you notice a regression in bundle size or paint timing.

## Reaching further: the aggressive tier

By default the compiler is conservative - it extracts only what it can prove static and leaves the
rest to the runtime. Some constructs it could read but deliberately declines, like a `{...obj}`
spread. Opt into extra extraction with `optimizationLevel: 'aggressive'`:

<CodeBlock lang="ts" code={`// vite.config.ts
motif.vite({ optimizationLevel: 'aggressive' }) // default: 'safe'`} />

In aggressive mode two extra cases extract that the safe tier leaves to the runtime:

- A fully-static **object spread** (`{...{ p: 8 }}`, or `{...CONST}` resolving to a literal object)
  is inlined into explicit props and baked like any other static prop.
- A **static-branch ternary** on the web - `p={cond ? 4 : 8}` with both branches resolvable to one
  scalar value - is baked to a conditional inline style (`style={{ padding: cond ? 4 : 8 }}`): the
  condition stays at runtime, the values are pre-resolved.
- A **`useMedia` read** on the web - `flexDirection={media.md ? 'row' : 'column'}`, where `media`
  comes from `useMedia()` - is rewritten to the equivalent responsive prop
  (`{ base: 'column', md: 'row' }`) and compiled to a CSS media query, so the prop stops depending
  on the runtime hook. This one is a semantics-preserving rewrite (same visual result, better SSR),
  not a byte-identical pre-resolution.
- A **nested `styled()` chain** - `styled(styled(Box, ...), ...)`, base-only at every level - is
  resolved through to the underlying element with its bases merged, so the whole chain collapses to
  a plain element (the safe tier already flattens a single `styled()` over a primitive).

For the pre-resolutions, byte-for-byte parity holds - extracted output is identical to what the
runtime emits, so a half-compiled codebase still dedupes. Anything not provably static (a dynamic
spread, a ternary with a dynamic branch, a `media` that isn't a `useMedia()` result, a prop that
would conflict on the cascade) bails exactly as before, and an `onAggressiveReport` callback
surfaces what was inlined, erased, and bailed per file. The default stays `safe` so adopting the
compiler never changes output; aggression is a separate, explicit choice. See [Compiler
optimization levels](/adr/0010-optimization-levels).

## Atomic output

`atomic: true` compiles each static declaration to its own shared class instead of an inline
style, so a declaration repeated across the app ships once:

<CodeBlock lang="ts" code={`// vite.config.ts
motif.vite({ atomic: true })`} />

<CodeBlock lang="tsx" code={`<Box p="16px" bg="#3b82f6" />
// → <div className="a-dwf4oy68dw a-1om2idl6nzx" />
// .a-dwf4oy68dw { padding: 16px; }
// .a-1om2idl6nzx { background-color: #3b82f6; }`} />

A declaration becomes an atom only when nothing else on the element touches the same property.
`p` with `pt`, a base value with its breakpoint value, or a base value with its `:hover` value
keep the default output for that element. Shared atoms land in the sheet in whatever order the
first module using them was built, so two atoms that override each other could resolve either
way; leaving those out is what keeps the cascade the same as the default output.

**It is not the smaller choice today.** `yarn workspace @usemotif-bench/render css-size` compiles
300 generated components (727 rendered elements, with one in three carrying a hover state) in
each library and gzips the stylesheet and the server-rendered markup:

| Output | CSS | Markup | Total |
| --- | --- | --- | --- |
| motif, default | 169 | 4247 | 4416 |
| motif, atomic | 814 | 4110 | 4924 |
| StyleX | 620 | 3639 | 4259 |
| Panda | 877 | 3731 | 4608 |

Gzip collapses repeated inline styles almost as well as repeated class names, and motif's atom
names are longer than StyleX's. Use atomic output when inline styles are the problem, such as a
`style-src` Content Security Policy without `'unsafe-inline'`, or a stylesheet that must be
cached across pages, rather than for size. `cssLayer` also turns base props into classes, one per
element.
