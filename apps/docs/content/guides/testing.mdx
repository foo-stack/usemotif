# Testing

<Lede>
  motif renders real elements, so most component tests are ordinary Testing Library tests. For the
  cases where you need to assert on resolved styles, `@usemotif/test-utils` carries a conformance
  suite and a pair of Vitest matchers.
</Lede>

<ArticleMeta />

## Test components the ordinary way

A `<Box>` renders a real `<div>`; a `<Pressable>` renders a real button-like element with its
ARIA attributes set. There is nothing motif-specific to mock - render the component under a
`<ThemeProvider>` and assert with `@testing-library/react` as you would for any React component.

<CodeBlock lang="tsx" filename="SignInForm.test.tsx" code={`import { render, screen } from '@testing-library/react';
import userEvent from '@testing-library/user-event';
import { ThemeProvider } from 'usemotif';
import { lightTheme } from './theme';
import { SignInForm } from './SignInForm';

function renderWithTheme(ui: React.ReactElement) {
  return render(
    <ThemeProvider themes={[lightTheme]} active="light">
      {ui}
    </ThemeProvider>,
  );
}

test('submits the entered credentials', async () => {
  const onSubmit = vi.fn();
  renderWithTheme(<SignInForm onSubmit={onSubmit} />);

  await userEvent.type(screen.getByLabelText('Email'), 'a@example.com');
  await userEvent.click(screen.getByRole('button', { name: 'Sign in' }));

  expect(onSubmit).toHaveBeenCalledOnce();
});`} />

Query by role and label, not by class. motif's generated class names - `m-1a2b3c` - are stable
hashes, but they are an implementation detail; a test that asserts on them breaks the first time
a style prop changes. The accessible name and role are the contract worth testing.

<Callout variant="info" title="One ThemeProvider wrapper">
  Wrap every render in a `<ThemeProvider>` so token references resolve. A shared `renderWithTheme`
  helper - or Testing Library's `wrapper` option in a custom render - keeps it out of each test.
</Callout>

## Assert on resolved styles

When the thing under test *is* the styling - a `styled()` component with variants, a responsive
prop - assert on what resolved. `@usemotif/test-utils` ships two Vitest matchers for this.
Register them once in a setup file.

<CodeBlock lang="ts" filename="vitest.setup.ts" code={`import { expect } from 'vitest';
import { motifMatchers } from '@usemotif/test-utils';

expect.extend(motifMatchers);`} />

The matchers operate on a `RendererOutput`: the normalised, theme-resolved styles of one rendered
element. On the web, `renderStyles` from `@usemotif/react/testing` renders any element, your own
`styled()` components included, and returns one. Pass the theme you render with, so token values
read back as the theme resolves them. `toHaveStyle` checks the unconditional style; `toHaveStyleAt`
checks a scoped rule, keyed by an `@media`, `@container`, or pseudo-selector prefix.

<CodeBlock lang="tsx" filename="Tag.test.tsx" code={`import { renderStyles } from '@usemotif/react/testing';
import { theme } from './theme';
import { Tag } from './Tag';

const out = renderStyles(<Tag tone="loud" p={{ base: '$space.1', md: '$space.3' }} />, theme);

expect(out).toHaveStyle({ fontWeight: 700, padding: 4 });
expect(out).toHaveStyleAt(':hover', { opacity: 0.8 });
expect(out).toHaveStyleAt('@media (min-width: 768px)', { padding: 12 });`} />

`renderStyles` is web only. On React Native, assert on the rendered output with your usual testing
library.

Both are subset matches - extra keys are tolerated, so a renderer adding delivery-specific styles
does not break the assertion.

## Assert what assistive technology hears

`motifMatchers` includes three accessibility matchers that read the same on both platforms. Pass
a DOM element on web, or a React Native test instance from `@testing-library/react-native`:

<CodeBlock lang="tsx" code={`expect.extend(motifMatchers);

// web
const trigger = screen.getByText('Shipping details').closest('button');
// native
const trigger = screen.getByText('Shipping details').parent;

expect(trigger).toHaveRole('button');
expect(trigger).toHaveAccessibleName('Shipping details');
expect(trigger).toBeExpanded();`} />

Roles are ARIA's names on both sides: `<h2>` and `accessibilityRole="header"` are both
`heading`, `<img alt="">` is `presentation`, and an `<input type="email">` is a `textbox`. The
name comes from `aria-labelledby`, `aria-label`, `alt` or a form control's `<label>` on web, from
`accessibilityLabel` or `aria-label` on native, and from text content otherwise. `toBeExpanded`
reads `aria-expanded`, or `accessibilityState.expanded` on native, and throws on an element that
reports no expanded state at all, so a negated assertion can't pass by accident.

`accessibleFacts(target)` returns all three at once.

## Run the conformance suite

`@usemotif/test-utils` exists for a larger job: proving that two renderers - web and native -
resolve the same props to the same styles. `standardCases` is the renderer-agnostic case list;
`assertConformance` renders one case through an adapter and throws on any mismatch.

<CodeBlock lang="ts" filename="conformance.test.ts" code={`import { describe, it } from 'vitest';
import { assertConformance, standardCases } from '@usemotif/test-utils';
import { myAdapter } from './my-adapter';

describe('renderer conformance', () => {
  for (const c of standardCases) {
    it(c.name, () => assertConformance(myAdapter, c));
  }
});`} />

This matters to you when you maintain a design system on top of motif and want to prove a wrapper
layer has not changed resolution, or when you author a custom renderer. The adapter is the seam:
it renders a `ConformanceCase` and normalises the result into `RendererOutput`. The internal
`@usemotif/react` and `@usemotif/react-native` packages each supply one; `standardCases` runs
unchanged against both.

To extend coverage, append your own cases - they are plain objects of the same shape.

<CodeBlock lang="ts" code={`import { standardCases, type ConformanceCase } from '@usemotif/test-utils';

const extraCases: readonly ConformanceCase[] = [
  {
    name: 'Box / brand spacing token',
    primitive: 'Box',
    props: { p: '$brand.gutter' },
    theme: brandTheme,
    expectStyle: { padding: 20 },
  },
];

for (const c of [...standardCases, ...extraCases]) {
  it(c.name, () => assertConformance(myAdapter, c));
}`} />

`defaultTestTheme` is the small fixed theme the standard cases resolve against - reach for it
whenever a unit test needs a stable theme without pulling in the full `@usemotif/tokens` defaults.
